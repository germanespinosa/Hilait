# How Hilait protects credentials

This describes Hilait 0.1.27 and the hardened Linux service configuration in
[`deploy/hilait.service`](../deploy/hilait.service). It distinguishes encrypted
storage from access to secrets while the service is running.

## Threat boundary

The recommended Linux installation runs Hilait as a dedicated, non-login
`hilait` account. Other SSH users without root, sudo, access to that account,
or write access to the installed application cannot read its data directory,
the persistent encryption key, or its process memory. Hilait can open agent
connections without a human re-entering machine passwords because the service
receives its encryption key at startup.

**Root on the Hilait host remains trusted.** Root can read the persistent key,
inspect a running process, replace the application, or capture a password at
its next use. Encryption on the same unattended host cannot make credentials
inaccessible to its root administrator. Do not give untrusted people root or
sudo on this host. A dedicated service account and systemd sandbox reduce
exposure to ordinary SSH accounts and unrelated services; they do not change
this root boundary.

## What is stored and how

| Data | At-rest protection |
| --- | --- |
| Saved machine names, hosts, usernames, settings, and trusted SSH host fingerprints | The complete `connections.json` and `known-hosts.json` records use Fernet authenticated encryption with a key derived from the active 160-bit OTP seed. The seed is itself encrypted under the master key. |
| Saved SSH password or private-key passphrase, saved sudo password | Each secret is encrypted under the independent 256-bit random master key, then stored inside the encrypted connection profile. Neither the password nor passphrase is returned by the profile API. |
| Machine authorizations | The complete `authorizations.json` record uses the OTP-seed-derived connection key. |
| Agent tokens | `agents.json` contains a SHA-256 lookup hash and a master-key-encrypted copy of each token. The full token is returned only when an administrator explicitly copies its configuration. |
| Admin recovery token and OTP seed | `admin.token` and `admin-otp.json` are master-key-encrypted. The admin token is not accepted for web access while OTP is enabled. |
| ntfy settings and token | The complete `ntfy.json` record is master-key-encrypted. |
| Activity-review provider API key | The `api_key` field in `review-settings.json` is master-key-encrypted. Other review settings are ordinary JSON inside the service-only directory. |
| Audit records and review results | Fernet encryption under the master key. Audit entries also form a SHA-256 hash chain; the chain does not prevent deletion by an account that controls the store. Plaintext exports must be protected separately. |
| Built-in HTTPS server private key | `lan.key` is encrypted PKCS#8. Its password is derived with HMAC-SHA-256 from the master key using a separate context string. The public certificate in `lan.crt` is not secret. |

Fernet, as implemented by the `cryptography` package, uses AES-128-CBC with a
fresh IV and HMAC-SHA-256 authentication. The random master key is generated by
Fernet's secure key generator. OTP codes are **not** encryption keys; the
long-lived random OTP seed derives the connection-record key. The OTP seed is
stored encrypted under the master key so unattended agent connections remain
possible. Replacing or resetting the OTP seed deletes machine connection data.

The service never intentionally places SSH or sudo passwords in agent MCP
responses or audit records. Human terminal keystrokes are redacted, but remote
terminal output and file contents can contain sensitive information and are
included in encrypted audit records. A command can also print a secret, so
avoid printing credentials in terminals.

An SSH private-key **path** saved in a machine profile refers to a separate
file. Hilait does not import or encrypt that file. If private-key login is
used, place the key in a service-owned directory such as
`/var/lib/hilait/keys`, mode `0600`, and select that path in the connection.
The hardened service cannot read keys under `/root` or other users' home
directories. Passphrase-protected keys retain their own encryption.

Agent-side MCP tokens are different: an agent client that needs to reconnect
unattended must retain its token on **that client**. Hilait does not control
the security of another computer's MCP configuration or client token cache.

## Where the master key lives

In the recommended Linux service, the original random `master.key` is held at
`/etc/hilait/master.key`, owned by root, mode `0400`. systemd's
`LoadCredential=` provides a private runtime copy to the `hilait` process in
`$CREDENTIALS_DIRECTORY/master.key`. The application fails closed if that
credential is missing, malformed, redirected by a symlink, or accessible to
other Unix accounts. No copy of the key remains in `/var/lib/hilait`.

`/var/lib/hilait` belongs to `hilait:hilait` with mode `0700`; secret files
are regular, single-link files with mode `0600`. The application refuses
symlinked or broadly readable secret files instead of following them. The
systemd unit also gives the process no Linux capabilities, blocks privilege
gain, hides home directories, restricts writable paths, and uses a private
temporary directory. The service must still have network access for SSH,
model providers, and ntfy.

On Windows and macOS, or when run manually without a systemd credential,
Hilait keeps `master.key` in its per-user data directory with owner-only
permissions where supported. That convenience mode is not equivalent to the
hardened Linux service. A login account that can run Hilait as the same user
can decrypt its data. On Windows, protect the account and data-directory ACLs;
POSIX mode checks do not apply there.

## Migration to the dedicated Linux service

1. Stop Hilait. Preserve a root-only backup of its current data directory and
   `/etc/systemd/system/hilait.service`. Backups containing both data and key
   are sufficient to decrypt credentials, so store them as sensitive material.
2. Create the `hilait` system account without a login shell. Move the existing
   data directory to `/var/lib/hilait`, preserving every file. Before changing
   ownership, move its `master.key` to `/etc/hilait/master.key` and set that
   file to `root:root`, mode `0400`.
3. Set `/var/lib/hilait` to `hilait:hilait`, mode `0700`, and its existing
   regular files to mode `0600`. Inspect any saved SSH private-key paths:
   relocate needed keys into a `hilait`-owned, mode-`0700` directory, with
   mode-`0600` files, and update those connection paths after startup.
4. Install [`deploy/hilait.service`](../deploy/hilait.service) as
   `/etc/systemd/system/hilait.service`. Keep the application virtual
   environment at `/opt/hilait-venv` readable by `hilait` but writable only
   by root. Run `systemctl daemon-reload`, start the service, and check its
   status, `/health`, saved machines, and a real SSH login. The first start
   migrates the legacy plaintext admin token and unencrypted LAN private key
   to encrypted files without changing the admin token or certificate.
5. Only after verification, remove or securely retain the original root-home
   data copy. Deleting a file on an SSD does not reliably erase old blocks;
   protect old backups and snapshots too.

Losing `/etc/hilait/master.key` makes the encrypted data, OTP seed, saved
credentials, and encrypted HTTPS key unrecoverable. Back it up securely along
with the data. Key rotation requires a separate decrypt-and-re-encrypt
migration; simply replacing the file destroys access.

## Runtime limits

Hilait decrypts a saved secret in process memory when it needs to authenticate
an SSH connection, perform approved sudo, use ntfy, or call a review provider.
Python and dependent libraries may retain copies until garbage collection;
Hilait cannot promise immediate zeroization. A privileged operator or a
compromised `hilait` process can capture secrets while the service runs.
The application also cannot protect secrets a user types into an external
terminal or stores in a separate private-key file.

The security goal here is authenticated encryption at rest, strict isolation
from ordinary SSH users, minimal operating-system privileges, and explicit
human approval for agent connections. It is not protection against root on the
same live server.
